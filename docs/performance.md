# 성능 — 3,000마리 검증 (기획서 프롬프트 2)

목표: **3,000마리 동시 @ 60fps @ 1080p.** 60fps 예산은 프레임당 16.67ms.

측정 환경은 클라우드 컨테이너(소프트웨어 렌더러 llvmpipe)다. **GPU 프레임타임은 의미가 없으므로
여기서는 CPU(=GDScript) 비용과 드로우콜만 근거로 삼는다.** 실제 GPU 수치는 각자 머신에서
`tests/stress_test.tscn` 을 띄우고 F3로 확인할 것.

## 결과

`tools/bench.sh` — 적을 반경 900 원판에 고르게 뿌리고 물리 1틱 비용 측정 (단위 ms)

| 적 | 해시 재구성 | 이동+분리 | 버퍼 갱신 | 합계 | 60fps 예산 대비 |
|---|---|---|---|---|---|
| 500 | 0.35 | 0.47 | 0.16 | 0.99 | 6% |
| 1,000 | 0.44 | 1.26 | 0.34 | 2.04 | 12% |
| 2,000 | 0.64 | 3.47 | 0.60 | 4.72 | 28% |
| 3,000 | 0.86 | 5.38 | 0.92 | 7.19 | 43% |
| 4,000 | 1.07 | 7.83 | 1.19 | 10.08 | 60% |

`tools/stress.sh` — 3,000마리를 계속 유지하며 실제로 한 판 진행 (더 빽빽한 최악 조건)

```
목표 3000마리 / 실제 2987마리
시뮬 6.04ms  버퍼 1.09ms  (물리 1틱)   → 합계 7.13ms = 예산의 43%
드로우콜 46   비디오메모리 87.9MB
```

위 수치는 **실아트를 넣은 뒤** 다시 잰 것이다 (2048x2048 아틀라스 + 노멀맵).
플레이스홀더(작은 도형) 시절 8.7ms 에서 오히려 줄었다 — 아틀라스가 커져도
적 전체가 MultiMesh 하나라 드로우콜과 시뮬 비용이 텍스처 크기에 안 묶인다.
드로우콜이 40 → 46 으로 는 건 M3~M4 에서 늘어난 UI 와 해저드 때문이다.

> 같은 세션에서 before/after 를 재라. 컨테이너 CPU 편차가 커서 다른 날 잰 숫자와
> 비교하면 없는 회귀를 만들어 낸다 (실제로 1.8배 "회귀" 를 쫓다가 HEAD 가 똑같이
> 나오는 걸 확인한 적이 있다).

**드로우콜은 적 3,000마리를 넣어도 거의 늘지 않는다.** 적 전체가 MultiMesh 하나라
드로우콜 1개고, 나머지 증가분은 HUD 텍스트 글리프와 픽업이다.

## 처음엔 미달이었다 — 26.95ms (예산의 162%)

M0를 그대로 재면 3,000마리에서 26.95ms가 나왔다. 병목은 전부 `EnemyManager._move`의
군집 분리였다. 네 가지를 고쳐 26.95 → 7.19ms (3.7배)로 줄였다.

| 고친 것 | 3,000마리 이동+분리 |
|---|---|
| (시작) 적마다 `hash_grid.query_circle()` 호출 | 26.22ms |
| ① 격자 내부 배열을 지역 변수로 받아 이웃 검사를 인라인 | 10.28ms |
| ② 셀 좌표를 int 하나로 접어 후보 필터를 1회 비교로 | 6.87ms |
| ③ 분리를 3프레임에 1번만, 힘은 3배 | (②에 포함) |
| ④ 셀 크기 64 → 32 | 5.38ms |

### ① 메서드 호출 제거
GDScript에서는 적 1마리마다 메서드를 부르는 것 자체가 비싸다. `SpatialHash`가 내부 배열
(`counts`/`items`/`cell_key`)을 그대로 넘겨주고, `EnemyManager`가 셀을 직접 훑는다.
읽기만 하므로 CoW 덕분에 배열 복사도 일어나지 않는다.

### ② 셀 키 패킹
해시 충돌을 걸러내려면 후보마다 셀 좌표를 확인해야 하는데, `cell_x[j] != cx or cell_y[j] != cy`
는 배열 2번 읽고 2번 비교한다. `cx * 2^32 + cy` 로 접어 두면 1번 읽고 1번 비교다.
GDScript int는 64비트라 충돌이 없다.

### ③ 분리 주기
분리를 60Hz로 돌 이유가 없다. 3프레임에 1번(20Hz) 계산하고 힘을 3배로 주면 평균 밀어내는
양은 같고 비용은 1/3이다. 눈으로는 차이가 안 보인다.
추가로 플레이어에서 1,300px보다 먼 적은 분리를 건너뛴다(화면 반대각이 약 1,100px이라
겹쳐 있어도 안 보인다).

### ④ 셀 크기
기획서 6.2는 64px이라고 적었지만, 셀 크기는 **분리 계산 기준**으로 정해야 한다.
무기 질의는 0.8초에 한 번이고 분리는 적 1마리마다 매 프레임이기 때문이다. 실측:

| 셀 | 3,000마리 이동+분리 |
|---|---|
| 32px | 5.38ms |
| 48px | 5.73ms |
| 64px | 6.65ms |
| 96px | 8.97ms |

## 절대값보다 상대값을 볼 것

이 표의 절대 수치는 **측정 당시 컨테이너가 받은 CPU 슬라이스에 따라 크게 흔들린다.**
같은 커밋을 다른 시점에 재면 3,000마리 합계가 6.9ms 였다가 11.2ms 로 나오기도 한다.
그래서 최적화를 판단할 때는 **반드시 같은 세션에서 before/after 를 나란히 재라.**
(실제로 M2 작업 중 "1.8배 느려졌다"고 놀랐는데, HEAD 를 같이 재보니 HEAD 도 똑같이 느렸다.
바뀐 코드의 실제 비용은 +0.2ms 였다.)

## 앞으로 조심할 것

- 이동+분리 비용은 **적 수에 대해 초선형**이다(밀도가 오르면 셀당 후보가 늘어서).
  4,000마리에서 이미 예산의 60%다. 적을 더 늘릴 거면 여기부터 다시 잰다.
- 새 기능을 붙일 때마다 `tools/bench.sh` 와 `tools/stress.sh` 를 돌려서
  3,000마리 수치가 나빠지지 않았는지 확인할 것. (CLAUDE.md 규칙 5)
- 아직 GPU 쪽은 검증되지 않았다. M2에서 실제 아트와 셰이더를 넣은 뒤 실제 GPU에서
  다시 재야 한다. 그게 기획서가 "아트 넣기 전에 성능 검증"이라고 못 박은 이유다.

## 모바일 목표 (세로 전환 이후)

**이 컨테이너에서 폰 성능은 측정할 수 없다.** 여기서 재는 건 컨테이너 CPU +
llvmpipe 소프트웨어 렌더러다. 실제 폰은 CPU 가 약한 대신 GPU 는 훨씬 낫다.
두 축이 반대로 움직이므로 여기 프레임률로 폰을 추정하면 틀린다.

| 여기서 잴 수 있는 것 | 폰에 대해 말할 수 있는가 |
|---|---|
| CPU 시뮬 비용 (해시·이동·분리) | 배수를 곱해 환산 가능 |
| 드로우콜·정점 수·VRAM | 기기와 무관하게 유효 |
| 프레임률 | ✗ 소프트웨어 렌더러라 무의미 |
| 발열·배터리 | ✗ 실기에서만 |

### CPU 예산 역산

`tools/bench.sh` 실측(컨테이너)과, 폰 CPU 가 이 정도 루프에서 2~3배 느리다는
가정으로 환산한 값이다.

| 적 수 | 컨테이너 | ×2.0 | ×2.5 | ×3.0 | 60fps 판정 |
|---|---|---|---|---|---|
| 500 | 1.06 | 2.12 | 2.65 | 3.18 | 여유 |
| 1,000 | 2.11 | 4.22 | 5.27 | 6.33 | 여유 |
| 1,500 | ~3.4 | 6.8 | 8.5 | 10.2 | **안전선** |
| 2,000 | 4.99 | 9.98 | 12.48 | 14.97 | 빠듯 |
| 3,000 | 7.80 | 15.60 | 19.50 | 23.40 | 초과 |

60fps 예산은 16.67ms 이고, **적 시뮬은 그중 절반(8.3ms)까지가 안전선**이다.
나머지 절반은 무기·투사체·해저드·렌더·GDScript GC 몫이다.

### 정한 값

`Settings.max_enemies` — 기본 **1,500**, 저사양 프리셋 **800**.

보통 플레이에서는 이 상한에 잘 안 닿는다 (완주 판의 최대 동시 적이 1,000 남짓).
밸런스를 바꾸려는 값이 아니라 최악의 순간에 프레임이 무너지지 않게 하는 안전선이다.
